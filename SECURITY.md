# Central data security — implementation design and remaining gates

**Status note (2026-11-10):** this page is the original design and its list of remaining gates. The shared-shop functions described in it now run on the production Supabase project; see [docs/release/CURRENT_STATUS.md](docs/release/CURRENT_STATUS.md). The mandatory tests listed below are still the checklist for the security audit. Local browser PIN and IndexedDB records are not server authentication and are not tamper-proof. No shared owner/staff PIN; auth identities must be linked to a vetted business membership and a shop assignment. Device provenance is independently validated by a trusted enrollment process (device ID alone is not a secret). Revalidate revocation on each ingest; offline writes accepted locally while later server-denied operations are preserved in a review queue.

Migrations use public tables with RLS and **no direct browser INSERT/UPDATE/DELETE** to financial tables. Authenticated owner/manager SELECT is scoped by active membership. Only a separately audited trusted ingestion endpoint/RPC may apply operations after verifying authenticated actor, device enrollment, shop authorization, payload digest, version, and invariant accounting. Do not expose a write-capable SECURITY DEFINER RPC without those checks and security-negative tests. No service-role keys in clients; secrets are server only. Revoke grants before enabling the Data API; RLS is not a substitute for grants, and views must be `security_invoker` or inaccessible to browser roles. Edge functions must use verified Auth JWT and safe server-only credentials if privileged writes are required. Audit tables are append-only to application roles, with optional externally stored digest checkpoints to detect privileged tampering. An append-only table alone does not prevent a database superuser from changing history.

Pending mandatory tests: owner A cannot read business B, unauthorized shop reads, forged staff and device, unauthenticated RPC, UPDATE/DELETE, direct INSERT, duplicate operation with conflicting digest, revoked-offline replay, forced logout/session expiry, and statement verification. Obtain real PostgreSQL test-environment evidence before any deployment.
