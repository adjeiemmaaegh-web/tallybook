# V43 sync enrollment and delivery checkpoint — 2026-10-27

This is a development checkpoint for the owner's five completion gates. The app remains **NO-GO** for production. The connected live Tallybook Supabase project was not changed, no payment was enabled, and no deployment or PR was made.

## Implemented on the development branch

1. **Identity and device binding:** The existing owner-issued, one-use invitation can now be redeemed by the authenticated target with an Ed25519 proof-of-possession signature. It binds company, shop, account, staff ID, device ID and public key in one serializable transaction. Owner revocation changes the server-owned key status atomically; the signed-sale verifier rejects subsequent uploads from that key. The API returns `publicKeyBound:true, hardwareBound:false`: a browser-held key is not hardware attestation. Local key creation/storage, an enrollment UI/route, staff provisioning, rotation and recovery are still missing.
2. **Sale delivery candidate:** `signedSaleEnvelope.ts` signs the exact local sale event with a non-extractable key. `signedSaleDelivery.ts` reconstructs missing outbox metadata from the durable local sale event, validates its digest, uses an explicit HTTPS upload with no cookies or redirects, and leaves ambiguous failures pending. The existing `uploadOnePendingOperation` still controls acknowledgement after server-receipt comparison. No automatic uploader or user-facing sync action is wired. Refund, purchase, supplier, shift and repayment events still have no remote ingestion path.
3. **Supabase isolated test project:** With the owner's selection of the current Tallybook organization, a separate project `lmneuqxfyxplrxjswpma` was created in `eu-west-2`. The existing UUID ownership and company-binding baseline, the UUID signed-sale candidate, and the device enrollment extension migrated successfully there. An additive test-only migration bound `company_device_keys.staff_id` to a staff record. Final read-only structural query: **14 public tables, all 14 with RLS, zero `anon`/`authenticated` table write grants, and a non-null staff-key binding**. Security advisor findings are informational `rls_enabled_no_policy` on ten intentionally server-only tables with no browser grants; see [Supabase's advisory](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). This is a schema check, **not** a two-account RLS or real Auth acceptance test. No synthetic Auth users were inserted directly into Supabase.
4. **Transport boundary:** `/api/central/sales` is mounted **disabled** in the shipped server. Its injectable handler requires direct TLS, exact configured origin, a verified bearer session, JSON, no cookies and rate limiting. It has no production pool or configured origin. A test-only handler invocation passed; live financial upload remains unavailable.
5. **Verification and release:** Full client Vitest **1,021/1,021** across 127 files; native `qa/*.test.mjs` **429/429**; focused identity/ingestion **26/26**; Chromium release, offline and local-auth browser checks **3/3 each**; TypeScript and production build passed. Raw logs are under `docs/central/evidence/v43-*`. After the full client run, a final check was added to reject an account switch immediately before upload. Its exact-source focused client tests passed **4/4**, and TypeScript/build passed again; the 1,021-test result predates only this final guard. The first native attempt had nine failures: eight sandbox permissions for loopback/disposable Git and one genuine ambiguous import. The import was fixed; a permission-enabled full rerun passed 429/429. Earlier focused Vitest initially failed due sandbox Temp rename and one test mock-hoisting issue; both were fixed before the passing focused run.

## Reproduce

From the repository root after installing the lockfile dependencies:

```powershell
node --test qa/central-sale-uuid-schema.test.mjs server/tests/centralEventTrust.test.mjs server/tests/centralSaleUploadRoute.test.mjs server/tests/storeDeviceEnrollment.test.mjs server/tests/storeDeviceEnrollmentPostgres.test.mjs
node_modules/.bin/tsc.cmd --noEmit --pretty false
npm.cmd run build
```

For the full client suite, set `TEMP` and `TMP` to a writable `client/.test-tmp` first, then run `vitest` from `client` with one worker. Native preview and Git fixture tests require loopback and temporary Git permissions. The disposable Supabase migration ledger names are `test_business_identity_baseline`, `test_company_binding_baseline`, `test_uuid_central_sale_candidate`, `test_uuid_device_key_enrollment`, and `test_uuid_device_staff_binding`. Do not replay the original `tb_*` draft migrations on the live project.
